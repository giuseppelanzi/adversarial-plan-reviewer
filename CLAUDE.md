# CLAUDE.md

Working conventions for this repo. The README and `docs/internals.md` are the source of truth for how the plugin behaves and why: the README for what a user sees and does, `docs/internals.md` for how it works, *Known traps* included. This file only holds what is needed to change it without breaking it. Read *Known traps* in `docs/internals.md` before touching a skill.

## Language

Everything in this repo is English: files, branch names, commit messages, PR titles and bodies, this file. The only non-English strings allowed are deliberate examples of multilingual behaviour, like the Italian request and `## Fonti lette` in the README.

The plugin's *output* follows the language of the conversation or the document. That rule lives in three places — both critics and the response protocol — and must stay in all three. The summary Claude gives the user before a review follows the conversation too, by section 0 of each skill.

## Layout

The plugin is `plugin/`, and that folder is what is submitted to the plugin directory. Everything else at the root — this file, `.claude/skills/craft-release`, `docs/`, the root `LICENSE` and `.claude-plugin/marketplace.json` — is for maintainers and GitHub, and never ships. The README is the exception: `plugin/` has none of its own, so the directory takes the root's (`validate` says so). The directory refuses this file and any `.claude/` folder in what it reads, which is why the split exists (`docs/internals.md`, *Known traps*). Paths in this file start at the repo root; inside `plugin/` the skills name their files through `${CLAUDE_PLUGIN_ROOT}`.

## Releases

- The user decides when to bump `version` in `plugin/.claude-plugin/plugin.json`. Never bump it unasked, not even to test an installed copy — a folder install reads the working tree, and `claude --plugin-dir plugin` loads it too (see *Verifying a change*).
- Branch: `<english-slug>`; on a release, `vX.Y.Z-<english-slug>`, e.g. `v0.8.0-timeout-signature`.
- Commit title: one sentence on what changed, prefixed `vX.Y.Z: ` on a release. The body is prose: the issue it closes, what was measured and how, and a `Verified:` line listing the checks that actually ran. If the plan was reviewed, say by whom and with what verdict.
- Every change of behaviour updates the docs in the same PR: the README when a user would notice it, `docs/internals.md` for how and why. A finding that cost a run to establish goes into *Known traps*, in `docs/internals.md`. Keep the README short: it is the plugin's front page, and detail belongs in `docs/internals.md`.
- The plugin's `name`, `adversarial-plan-reviewer`, is fixed once the plugin directory lists it: users have it installed under that name. The label shown is `displayName`, which can change. The listing icon, the PNG in `plugin/assets/`, is taken at the first submission only; changing it later does not change the listing. Do not name its file in any text file other than `plugin.json` and the README's image tag: the directory holds the plugin for it when a text file in what it reads names it (*Known traps*).
- Release notes and the GitHub release: `/craft-release`, once the release PR is merged. The tag is `vX.Y.Z` on the commit where main first carries the version; GitHub creates it when the user publishes the draft — never `git tag` or `git push --tags` from a session.

## Things that move together

- **The three skills.** `plugin/skills/antigravity/SKILL.md`, `plugin/skills/claude/SKILL.md` and `plugin/skills/codex/SKILL.md` share their structure: preflight (section 1), document location and critic choice (section 2), the ceiling tiers (section 3). Change one, check the others. Two differences are on purpose, both on agy: its probe runs on a model of its own, the rest of the rehearsal identical, and its tiers are twice the other two skills', since its review runs on Neon (`docs/internals.md`). What they do **not** share is the boundary: each transport keeps its reviewer read-only with its own mechanism — the agy agent's `tools` list plus the command list passed with `--settings`, the Claude allowlist, the Codex sandbox and `--disable` set. Do not carry one transport's mechanism into another: the agy reviewer's shell is held to six commands because of agy, where the permission list is what refuses a write, not because of a plugin rule.
- **`CRITIC` and `FRAMING`.** One unit in every bash block. Swapping the critic without the framing line makes the reviewer invent `file:line` references.
- **The two critics.** `plugin/reviewers/plan-critic.md` and `plugin/reviewers/doc-critic.md` keep identical severity levels and pass bar (`FAIL` iff at least one `[BLOCKING]`), and the same rule that a path outside the repository is not opened but listed under *What I could not verify* — the only fence on the Codex side, where such reads are not refused. They differ only in what counts as evidence and in what `[BLOCKING]` means.
- **The tier.** On the Claude side the timeout and `--max-turns` are one unit; raising one alone buys nothing. On the Codex side the tier is the external `timeout` alone, and it is required: Codex has no turn cap and no clock of its own. On the agy side it is `--print-timeout`, on a scale of its own — 600 / 1800 / 3600 against the others' 300 / 900 / 1800 — measured on Neon. Its numbers also live outside the tables, in prose: find them with the `git grep` of the tier sites before changing one.
- **The trace.** The `> **Review**:` stamp is defined in `plugin/reviewers/response-protocol.md` section 4, the *not run* lines — trivial plan, user declined — in the `description` of `plugin/skills/antigravity`. There is no backstop: the plugin ships no hook (`docs/internals.md`, *Known traps*), so the stamp rests on the skill and the `description` alone. The not-started stamps — `agy` not found, agent missing or outdated, review model not in `agy models`; `codex` not found, no `timeout` / `gtimeout` — appear in both section 4 and the section 1 of their skill.
- **The questions.** Two, and each has a question, a header and its options: `Review`, on a ready plan, with four — the three reviewers and `Approve without review`; `Reviewer`, on a request that names no reviewer, with the three reviewers alone. Both are written in the `description` of `plugin/skills/antigravity` — without the `Reviewer` wording, for room — and again in full in its section 0, with the one map from answer to skill; so is the rule that proposes plan mode before a non-trivial change made outside it. The `description`s of `plugin/skills/claude` and `plugin/skills/codex` point back to those questions: a reviewer picked in one is named. Before the `Review` question Claude sums the plan up for the user — what it does, the files it touches, its algorithms or design choices — by the `description` and section 0; section 0 of all three skills gives the same summary, before the preflight, on the first review of a plan whose summary the user has not had. The `description` is the copy that counts: it is the only text in context when the skill never loads — and outside plan mode it never does. It is cut at about 1,500 characters (`docs/internals.md`, *Known traps*): keep it under ~1,450, and make room before adding.
- **The reviewer agent.** `plugin/reviewers/agy-plan-reviewer.md` and the copy the user installs in `~/.gemini/config/agents/plan-reviewer.md`. Line 1 of the shipped file is a Markdown title that is never installed: it keeps the directory from reading agy's front matter as Claude Code's, so the shipped file never starts with `---`. The preflight compares the installed copy with the shipped file from line 2 on, byte for byte, so an edit below line 1 asks every user to install it again — say so in the commit. An edit to line 1 alone asks nothing of them.
- **The two licenses.** `LICENSE` at the root, where GitHub finds it, and `plugin/LICENSE`, which travels with the installed plugin. Identical.
- **The agy command list.** `AGY_SETTINGS` in both bash blocks of `plugin/skills/antigravity` — one string, identical — the commands the body of `plugin/reviewers/agy-plan-reviewer.md` names, the README's count of them, and `docs/internals.md`. A command on the list that the body does not name is one the reviewer does not know it has; one the body names that is not on the list is refused. Nothing goes on it that can run another program or write: that is why `rg` (`--pre`) and `find` (`-exec`, `-delete`) are not there.
- **The model pins.** Two on the agy side. The review's, `gemini-4-neon-xhigh`: in both bash blocks of `plugin/skills/antigravity` — the probe block carries it for the `agy models` check and the fallback — in its section 1 table and section 3 pin note, in the README, in `docs/internals.md`, in the stamp examples of the response protocol, and in `.claude/skills/craft-release`. The probe's, `gemini-4-hydrogen-low`: in the probe block, the section 1 table and the pin note, the README and `docs/internals.md` — not in craft-release, which lists the pins whose change breaks a review, and a probe pin that is not listed falls back to the review's. On the Codex side, `gpt-6.1-sol` with `model_reasoning_effort="high"` — one setting — in both bash blocks of `plugin/skills/codex`, in the README, in `docs/internals.md` and in the response protocol.

## Things this repo does not do

- No `--dangerously-skip-permissions` in the agy command, and never hidden in a wrapper script to get it past the classifier. No `--dangerously-bypass-approvals-and-sandbox` in the codex command, and never a flag of its `--sandbox read-only` / `--disable` set dropped to make a run pass.
- No instructions to the reviewer on which tools to use. Facts about its environment are fine; how to work is not. On the agy side the agent's `tools` list and the command list in `--settings` set the environment — the shell is held to that list by flags, never by the prompt, the same move as `--allowedTools` on the Claude side — and the agent's body states facts only: which commands run, which forms are refused. On the Codex side the sandbox and the `--disable` flags set the environment.
- No installing or editing agy's configuration from a session, the reviewer agent included: the skill hands the user the install command and stops.
- No review started on a plan without the user saying so, unless they asked for one outright. Claude proposes on each point; the user chooses which points to take.
- No context prepared for the reviewer — no summaries, extracted snippets or curated file lists. The document under review travels inline; the reviewer opens the repo itself. The summary before a review is for the user and never reaches the reviewer.
- No automatic retry and no fallback to another reviewer on failure. Report the error, offer the alternative in one line, wait.
- No hook of type `command`: the plugin directory refuses them from organizations that are not Verified. A `prompt` hook is allowed, but none ships.
- Skill `description`s are double-quoted in the front matter. Unquoted, a `: ` in the text makes it invalid YAML, which Claude Code tolerates and the directory refuses.
- Nothing inside a `.claude-plugin/` folder but its manifest: `marketplace.json` in the root one, `plugin.json` in `plugin/.claude-plugin/`. The icon lives in `plugin/assets/`, named by `icon` in `plugin.json`.
- Nothing in `plugin/` that the directory refuses from organizations that are not Verified: no `CLAUDE.md`, `CLAUDE.local.md` or `AGENTS.md` in any case, no `.claude/` folder, no `allowed-tools` beyond Read, Grep, Glob and LS, and no Markdown file that starts with `---` other than a `SKILL.md` whose front matter is `name` and `description` alone. Maintainer tooling stays at the root.
- No file in `plugin/` outside Markdown, text, JSON, YAML and PNG, JPEG, GIF, WebP or ICO images: the plugin directory refuses anything else from organizations that are not Verified, judging the content, not the name — no `#!` first line, no package manager configuration, no SVG, UTF-8 with no NUL bytes. `validate` does not catch it (`docs/internals.md`, *Known traps*).

## Shell

The Bash tool runs zsh, and the skills' bash runs there too:

- no `${PIPESTATUS[0]}` — redirect to a file and read `$?`;
- `${CLAUDE_PROJECT_DIR:-$PWD}`, never bare `$CLAUDE_PROJECT_DIR`;
- `</dev/null` on every `claude -p`, `agy` and `codex` call — `codex exec` reads stdin even with the prompt as an argument;
- every `agy` flag goes before `-p`;
- `--ask-for-approval never` goes before `exec`: it is a global `codex` option;
- `timeout` may be missing on macOS — the Claude skill already handles `gtimeout` and neither; the Codex skill accepts either name and stops when both are missing.

## Verifying a change

- `claude plugin validate plugin --profile directory` — the plugin's manifest, and much of what the plugin directory would refuse a submission for, but not the file types: for those, the `file --mime` loop in *Known traps*. `claude plugin validate .` checks the marketplace manifest at the root.
- `claude --plugin-dir plugin` — live loop, no install. `SKILL.md` edits apply at once.
- Installed from this repo as a folder marketplace, the plugin is read from the working tree in place — `claude plugin list` says *Read from:* `<repo>/plugin` — so a new session is all an edit needs: no update, no reinstall, no bump, no commit. Every session on the machine runs the branch checked out here. A plugin installed from GitHub, as users have it, is a copy under `~/.claude/plugins/cache/` that `claude plugin update` moves only on a new version string (`docs/internals.md`, *Known traps*).
- Judge a reviewer run by its output, never its exit code: an empty agy run exits 0, a failed `claude -p` run sets `.is_error` while exiting 0, and a codex run is the `VERDICT:` in its `--output-last-message` file — after the exit code, since `124` is the ceiling and a failed run whatever the file holds — never its stdout, which is the event stream.
